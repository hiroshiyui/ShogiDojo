# Shogi Dojo - Computer Shogi Studies Research Group

Academic research resources for studying NNUE (Efficiently Updatable Neural Network) evaluation in Shogi (Japanese Chess).

This repository provides a **HalfKAv2** training implementation built with PyTorch — the same family of NNUE architecture used in top-tier chess and Shogi engines — along with tools and documentation for training on position data generated by Shogi engines.

## What is NNUE?

NNUE is a neural network architecture designed for fast board-game evaluation. It was originally invented for Shogi by Yu Nasu in 2018. The key insight: instead of evaluating the entire board from scratch every time, NNUE uses an "accumulator" that can be **incrementally updated** when a single piece moves, making it fast enough for real-time game-tree search (millions of evaluations per second).

For a deeper dive into the architecture, see [doc/NNUE_Reference.md](doc/NNUE_Reference.md).

## Generating Training Data

Training data is generated by the included `gensfen` tool (`tools/gensfen/`), a Rust program that plays Shogi games against itself and records positions as training data.

### Building gensfen

Requires the [Rust toolchain](https://rustup.rs/) (rustc + cargo).

```bash
cd tools/gensfen
cargo build --release
```

The binary is at `tools/gensfen/target/release/gensfen`.

### Running gensfen

```bash
./tools/gensfen/target/release/gensfen \
    --depth 4 --threads 4 --positions 1000000 --output data/train.sfen
```

| Option | Default | Description |
|--------|---------|-------------|
| `--depth` | `4` | Alpha-beta search depth. Higher = better quality, slower. |
| `--threads` | `4` | Parallel game threads (each plays independent games). |
| `--positions` | (required) | Total number of positions to generate. |
| `--output` | `output.sfen` | Output file path (text SFEN format). |
| `--random-moves` | `8` | Random opening moves for position diversity. |

Each self-play game produces ~100–200 positions. The tool uses a material-only evaluation (Phase 1); future phases will use the trained NNUE for stronger self-play data (see `doc/TODO.md`).

### Output Format

One position per line, directly consumable by the Python training pipeline:

```
sfen <board> <side> <hand> <move#>\t<score>\t<result>
```

| Field     | Description                                               | Example                    |
|-----------|-----------------------------------------------------------|----------------------------|
| `board`   | SFEN board string (pieces on the 9x9 grid)                | `lnsgkgsnl/1r5b1/...`     |
| `side`    | Side to move: `b` (Black/Sente) or `w` (White/Gote)       | `b`                        |
| `hand`    | Pieces in hand (`-` if none)                               | `S2P` (1 Silver, 2 Pawns)  |
| `move#`   | Move number                                               | `1`                        |
| `score`   | Engine evaluation in centipawns (positive = good for STM)  | `100`                      |
| `result`  | Game result for STM: `1.0` = win, `0.5` = draw, `0.0` = loss | `1.0`                  |

### Alternative Data Sources

## Training

```bash
# Activate the virtual environment
source virtualenv/bin/activate

# Train with default configuration
python train.py

# Use a custom config
python train.py --config configs/my_experiment.yaml

# Resume from a checkpoint
python train.py --resume checkpoints/epoch_0050.pt
```

## Disk Space Requirements

The dominant cost is training data. Plan your disk budget based on the scale of your experiment:

| Component | Size | Notes |
|-----------|------|-------|
| Training data (text SFEN) | **5–100+ GB** | 100M positions ≈ 5 GB. Serious training uses 1B+ positions (~50 GB). |
| Binary data from gensfen | ~40 bytes/position | 100M positions ≈ 3.7 GB. Can be deleted after converting to text SFEN. |
| Single checkpoint | ~19 MB | Model weights (5M params) + Adam optimizer state |
| All checkpoints (default) | ~385 MB | 20 files (save every 10 epochs × 200 epochs) |
| Suisho5.7z (eval file) | ~23 MB | Included in repo |
| YaneuraOu source | ~150 MB | Git submodule |

**Recommended disk budget by experiment scale:**

| Scale | Positions | Training Data | Total Disk |
|-------|-----------|--------------|------------|
| Quick test | 1M | ~50 MB | **~1 GB** |
| Small run | 100M | ~5 GB | **~7 GB** |
| Full training | 1B | ~50 GB | **~55 GB** |

To reduce disk usage:
- Increase `save_every` in the config (e.g., 50 instead of 10) to keep fewer checkpoints.
- Delete the `.bin` binary after converting to `.sfen`.
- Generate fewer positions and train for more epochs (trades data quality for space).

## Configuration

All hyperparameters are set in `configs/default.yaml`. Key options:

```yaml
data:
  batch_size: 8192       # Positions per batch (reduce if OOM)
  num_workers: 4         # Parallel data loading processes

model:
  ft_out_dim: 256        # Feature transformer width (per perspective)
  l1_dim: 32             # Eval network hidden layer 1
  l2_dim: 32             # Eval network hidden layer 2

training:
  epochs: 200
  lr: 1.0e-3             # Adam learning rate
  lr_scheduler: "cosine" # "cosine" or "step"
  lambda_score: 1.0      # Weight for engine-score loss
  lambda_result: 0.5     # Weight for game-result loss
  score_scaling: 600.0   # Centipawn normalization factor
  save_every: 10         # Checkpoint frequency (epochs)
```

See `configs/default.yaml` for the full list with detailed comments.

## Model Architecture

ShogiDojo uses the **HalfKAv2** NNUE architecture (~5M parameters):

```
Sparse Input (19,638 possible features, ~40 active per position)
    ↓
Feature Transformer (shared weights, sparse lookup + sum)
    ├─ STM perspective  → 256-dim dense vector
    └─ NSTM perspective → 256-dim dense vector
    ↓
Concatenate → 512-dim
    ↓ ClippedReLU
Linear 512 → 32
    ↓ ClippedReLU
Linear 32 → 32
    ↓ ClippedReLU
Linear 32 → 1  →  Evaluation Score
```

- **STM** = Side-To-Move (the player whose turn it is)
- **NSTM** = Not-Side-To-Move (the opponent)
- **ClippedReLU** = `clamp(x, 0, 1)` — bounded activations for quantization compatibility

For a full explanation of HalfKAv2, king buckets, feature encoding, and loss functions, see [doc/NNUE_Reference.md](doc/NNUE_Reference.md).
