# Shogi Dojo - Computer Shogi Studies Research Group

Academic research resources for studying NNUE (Efficiently Updatable Neural Network) evaluation in Shogi (Japanese Chess).

This repository provides a **HalfKAv2** training implementation built with PyTorch — the same family of NNUE architecture used in top-tier chess and Shogi engines — along with tools and documentation for training on position data generated by Shogi engines.

## What is NNUE?

NNUE is a neural network architecture designed for fast board-game evaluation. It was originally invented for Shogi by Yu Nasu in 2018. The key insight: instead of evaluating the entire board from scratch every time, NNUE uses an "accumulator" that can be **incrementally updated** when a single piece moves, making it fast enough for real-time game-tree search (millions of evaluations per second).

For a deeper dive into the architecture, see [doc/NNUE_Reference.md](doc/NNUE_Reference.md).

```bash
# 1. Build YaneuraOu for training data generation
cd vendor/YaneuraOu/source
make clean && make evallearn
cd ../../..

# 2. Generate training data (self-play, ~1M positions)
#    You need an nn.bin eval file — see "Generating Training Data" below.
mkdir -p data
./vendor/YaneuraOu/source/YaneuraOu-by-gcc <<'USI'
setoption name Threads value 4
setoption name Hash value 2048
gensfen depth 6 loop 1000000 output_file_name data/train.bin eval_limit 3000
quit
USI

# 3. Convert binary data to text SFEN format (see below)
python scripts/convert_bin_to_sfen.py data/train.bin data/train.sfen

# 4. Train the NNUE model
source virtualenv/bin/activate
python train.py
```

## Generating Training Data

Training data is generated by the vendored [YaneuraOu](https://github.com/yaneurao/YaneuraOu) engine through self-play. The engine plays games against itself at a specified search depth and records every position with its evaluation score and game outcome.

### Step 1: Build YaneuraOu

You **must** build with the `evallearn` target — the standard `normal` build does not include the `gensfen` command.

```bash
cd vendor/YaneuraOu/source
make clean
make evallearn
```

Build options (edit the `Makefile` if needed):

| Option | Default | Alternatives |
|--------|---------|-------------|
| `TARGET_CPU` | `AVX2` | `AVX512`, `SSE42`, `ZEN3`, `APPLEM1`, `NO_SSE` |
| `COMPILER` | `clang++` | `g++` |
| `YANEURAOU_EDITION` | `YANEURAOU_ENGINE_NNUE` | Other NNUE variants (see Makefile) |

The resulting binary is `vendor/YaneuraOu/source/YaneuraOu-by-gcc`.

### Step 2: Obtain an Evaluation File

YaneuraOu needs an existing NNUE evaluation file (`nn.bin`) to perform the search that generates training data. You can:

- **Download** a pre-trained `nn.bin` from the [YaneuraOu releases](https://github.com/yaneurao/YaneuraOu/releases) or community resources.
- Place it at `vendor/YaneuraOu/source/eval/nn.bin` (the default search path), or set the path via the USI option `EvalDir`.

This project includes `data/Suisho5.7z` (not tracked in git), which is a copy of the Suisho5 eval file from the [YaneuraOu suisho5 release](https://github.com/yaneurao/YaneuraOu/releases/tag/suisho5). Extract it to get `nn.bin`:

```bash
7z x data/Suisho5.7z -ovendor/YaneuraOu/source/eval/
```

### Step 3: Run gensfen

The `gensfen` command is issued through the USI protocol (stdin). Set engine options first, then run `gensfen`:

```bash
./vendor/YaneuraOu/source/YaneuraOu-by-gcc <<'USI'
setoption name Threads value 8
setoption name Hash value 4096
gensfen depth 6 loop 100000000 output_file_name data/train.bin eval_limit 3000
quit
USI
```

Key `gensfen` parameters:

| Parameter | Default | Description |
|-----------|---------|-------------|
| `depth` | `3` | Search depth (higher = better quality, slower). 6–8 recommended. |
| `loop` | `8000000000` | Number of positions to generate |
| `output_file_name` | `generated_kifu.bin` | Output file path |
| `eval_limit` | `3000` | Skip positions with eval beyond this (centipawns) |
| `write_minply` | `16` | Don't record the first N plies (skip opening book moves) |
| `write_maxply` | `400` | Stop recording after this many plies |
| `random_move_count` | `5` | Random moves in the opening for position diversity |
| `random_move_maxply` | `24` | Apply random moves up to this ply |
| `save_every` | unlimited | Save to a new file every N positions |
| `random_file_name` | `false` | Append random suffix (useful for parallel generation) |

There is also a newer variant, `gensfen2019`, which uses node limits instead of depth for more consistent quality across hardware:

```
gensfen2019 search_depth 24 nodes_limit 10000 loop 100000000 output_file_name data/train.bin
```

**Parallel generation** across multiple machines:

```bash
# On each machine, use random_file_name to avoid collisions
gensfen depth 6 loop 100000000 output_file_name data/shard random_file_name true
# Produces: data/shard_<random_hex>.bin
```

### Step 4: Convert Binary to Text SFEN

YaneuraOu outputs a binary format (`PackedSfenValue`, 40 bytes per position) containing a Huffman-encoded board position, evaluation score, best move, and game result. ShogiDojo expects a text SFEN format.

Each line in the text format has:

```
sfen <board> <side> <hand> <move#> <score> <result>
```

| Field     | Description                                               | Example                    |
|-----------|-----------------------------------------------------------|----------------------------|
| `board`   | SFEN board string (pieces on the 9x9 grid)                | `lnsgkgsnl/1r5b1/...`     |
| `side`    | Side to move: `b` (Black/Sente) or `w` (White/Gote)       | `b`                        |
| `hand`    | Pieces in hand (`-` if none)                               | `S2P` (1 Silver, 2 Pawns)  |
| `move#`   | Move number                                               | `1`                        |
| `score`   | Engine evaluation in centipawns (positive = good for STM)  | `100`                      |
| `result`  | Game result for STM: `1.0` = win, `0.5` = draw, `0.0` = loss | `1.0`                  |

Full example line:

```
sfen lnsgkgsnl/1r5b1/ppppppppp/9/9/9/PPPPPPPPP/1B5R1/LNSGKGSNL b - 1	100	1.0
```

> **Note:** A conversion script (`scripts/convert_bin_to_sfen.py`) is needed to decode the binary format. You can also download pre-converted datasets from [Hugging Face (nodchip/shogi_hao_depth9)](https://huggingface.co/datasets/nodchip/shogi_hao_depth9).

### Step 5: Prepare Data Files

Split your data into training and (optionally) validation sets, then place them in `data/`:

```
data/
├── train.sfen    # Training positions (required)
└── val.sfen      # Validation positions (optional)
```

## Training

```bash
# Activate the virtual environment
source virtualenv/bin/activate

# Train with default configuration
python train.py

# Use a custom config
python train.py --config configs/my_experiment.yaml

# Resume from a checkpoint
python train.py --resume checkpoints/epoch_0050.pt
```

## Disk Space Requirements

The dominant cost is training data. Plan your disk budget based on the scale of your experiment:

| Component | Size | Notes |
|-----------|------|-------|
| Training data (text SFEN) | **5–100+ GB** | 100M positions ≈ 5 GB. Serious training uses 1B+ positions (~50 GB). |
| Binary data from gensfen | ~40 bytes/position | 100M positions ≈ 3.7 GB. Can be deleted after converting to text SFEN. |
| Single checkpoint | ~19 MB | Model weights (5M params) + Adam optimizer state |
| All checkpoints (default) | ~385 MB | 20 files (save every 10 epochs × 200 epochs) |
| Suisho5.7z (eval file) | ~23 MB | Included in repo |
| YaneuraOu source | ~150 MB | Git submodule |

**Recommended disk budget by experiment scale:**

| Scale | Positions | Training Data | Total Disk |
|-------|-----------|--------------|------------|
| Quick test | 1M | ~50 MB | **~1 GB** |
| Small run | 100M | ~5 GB | **~7 GB** |
| Full training | 1B | ~50 GB | **~55 GB** |

To reduce disk usage:
- Increase `save_every` in the config (e.g., 50 instead of 10) to keep fewer checkpoints.
- Delete the `.bin` binary after converting to `.sfen`.
- Generate fewer positions and train for more epochs (trades data quality for space).

## Configuration

All hyperparameters are set in `configs/default.yaml`. Key options:

```yaml
data:
  batch_size: 8192       # Positions per batch (reduce if OOM)
  num_workers: 4         # Parallel data loading processes

model:
  ft_out_dim: 256        # Feature transformer width (per perspective)
  l1_dim: 32             # Eval network hidden layer 1
  l2_dim: 32             # Eval network hidden layer 2

training:
  epochs: 200
  lr: 1.0e-3             # Adam learning rate
  lr_scheduler: "cosine" # "cosine" or "step"
  lambda_score: 1.0      # Weight for engine-score loss
  lambda_result: 0.5     # Weight for game-result loss
  score_scaling: 600.0   # Centipawn normalization factor
  save_every: 10         # Checkpoint frequency (epochs)
```

See `configs/default.yaml` for the full list with detailed comments.

## Model Architecture

ShogiDojo uses the **HalfKAv2** NNUE architecture (~5M parameters):

```
Sparse Input (19,638 possible features, ~40 active per position)
    ↓
Feature Transformer (shared weights, sparse lookup + sum)
    ├─ STM perspective  → 256-dim dense vector
    └─ NSTM perspective → 256-dim dense vector
    ↓
Concatenate → 512-dim
    ↓ ClippedReLU
Linear 512 → 32
    ↓ ClippedReLU
Linear 32 → 32
    ↓ ClippedReLU
Linear 32 → 1  →  Evaluation Score
```

- **STM** = Side-To-Move (the player whose turn it is)
- **NSTM** = Not-Side-To-Move (the opponent)
- **ClippedReLU** = `clamp(x, 0, 1)` — bounded activations for quantization compatibility

For a full explanation of HalfKAv2, king buckets, feature encoding, and loss functions, see [doc/NNUE_Reference.md](doc/NNUE_Reference.md).
